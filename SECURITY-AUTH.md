# Authentication hardening — web build 379

Build 380 follow-up: signup email verification and optional, session-bound email checks are documented in [EMAIL-SECURITY.md](EMAIL-SECURITY.md). The “verification off” statements below record the original build 379 rollout, not the current provider configuration.

## What changed

- Persistent member refresh credentials moved from `cineva.supabase.session` in localStorage to an AES-GCM authenticated, origin-bound `__Host-seven_refresh` cookie. It is Secure, HttpOnly, SameSite=Lax, Path=/, has no Domain attribute, and lasts 30 days with renewal. Access JWTs stay in memory for the existing bearer-authenticated APIs; the local cache contains only non-authoritative UI identity/preferences and expiry metadata. A script running through XSS can still act as an active user: this is risk reduction, not a claim that XSS is impossible.
- Existing installations exchange their old refresh token on their next successful online restoration. Only after the exchange succeeds does the new code replace the old stored session with the non-secret cache. An offline migration does not destroy the user's only existing renewable credential. No forced logout, password reset or reinstall is part of deployment. Existing open tabs should reopen to load the new client.
- Cookie mutations use same-origin JSON requests, reject foreign Origin and cross-site Fetch Metadata, and serialize login/refresh/MFA verification/logout through a browser-wide lock. Logout clears the server cookie and invalidates the Supabase session; a generation check rejects late client-side refresh completion. Offline logout retains a non-secret pending marker, prevents session restoration and retries at reconnection/next launch before any new sign-in. A transient failure after rotation retains the rotated HttpOnly cookie only for the retry. Cookies do not silently authorize the ordinary account APIs: those still require the short-lived bearer token and existing owner/session validation.
- Distributed throttling uses PostgreSQL atomic counters, shared across worker instances. Only server/service-role code can execute the rate RPC. The database sees HMAC-derived bucket identifiers, not email addresses, IPs, passwords or tokens. Login/signup get IP and IP+identity budgets; admin login, password changes, device unlock, parent-code operations and TOTP attempts are also bounded. Responses include 429 and Retry-After. Backend/protection failures fail closed rather than allowing unlimited guesses. Supabase's own Auth limits remain an additional layer, including for direct Auth calls.
- New passwords use a shared browser/server policy: 12+ characters, at most 72 UTF-8 bytes. No composition gimmicks or trimming of secrets. New signup and password changes check Have I Been Pwned's free Pwned Passwords range API server-side: only five SHA-1 hex characters are sent, with padded responses; a matching breached password is refused. Unavailable safety checks ask users to retry rather than approving unchecked passwords. Ordinary login does not impose the new-password rules on existing credentials.
- Account password changes still verify the current credential, clean up the temporary verification session, send `current_password` to Supabase's native password-update check, and never write an accompanying stale settings snapshot.
- Optional time-based authenticator 2FA is available from the main profile's Security settings. Setup requires the account password and a successful code before activation. Secrets appear only in the setup dialog, never in the account cache/settings queue; copying is an explicit user action. Abandoned setup can be cancelled; verified factors cannot be removed with that action. Disabling requires an AAL2 session and a fresh authenticator code. Keep a secure authenticator backup before enabling; this release does not invent a weaker email-based 2FA bypass or custom recovery-code system.
- Both API gates and restrictive RLS policies enforce AAL2 when the account has a verified MFA factor. Security-definer own-account RPCs are also guarded; their original implementations are no longer callable by anonymous/authenticated roles. Unenrolled accounts continue using ordinary sign-in. Existing device-session revocation remains enforced.
- Admin authorization was already server-side: signed HttpOnly cookie, constant-time credential check, private RPCs. It remains separate from client profile/admin labels; this change adds shared login throttling, not a client-side admin flag.
- CSP blocks inline/injected executable code and external script origins. Existing inline dashboard/download scripts use exact hashes (LF/CRLF variants), while inline styling remains supported for the current UI. Object embedding, base URL replacement, framing the app and MIME sniffing are restricted. Existing playback iframes remain allowed; startup visuals are unchanged.
- The local development server now delegates to the exact production API handler rather than maintaining an obsolete, weaker auth/settings copy. It binds to loopback and does not serve local credential JSON, hidden files, tests or QA code.

## Provider settings and intentional limits

Email verification remains **off and unchanged**, as requested; email ownership is a separate follow-up. Optional TOTP is not a substitute for verifying new email addresses. The provider's TOTP setting was already enabled, with 15-minute low-assurance expiry.

The provider minimum password length is set to 12 and native current-password-on-update is enabled after the compatible server build is deployed. Existing passwords still work at login. Secure email change stays enabled. The separate email-OTP-based "Secure password change" mode is not switched on behind the existing form's back.

Supabase's native, provider-wide leaked-password protection requires its Pro plan. This Free project instead gets the free range check on SEVEN's signup/password-change endpoints. This does not claim to enforce a leaked-password ban against clients deliberately calling Supabase Auth directly. No paid upgrade was made. A future stronger provider-wide guarantee requires the native feature or another appropriately supported provider control.

There was no public forgot-password/reset endpoint in the app to harden, and none is added here. A future recovery flow must validate actual recovery proof, preserve MFA requirements, use generic email responses, and reuse server throttling/password safety. It must not accept a normal bearer token as permission to bypass the current-password requirement.

## Deployment and verification

- Required existing server secrets: Supabase publishable and server secret/service-role keys, plus the stable 32+ character `SEVEN_DASHBOARD_SECRET`. Changing the signing secret invalidates refresh cookies and existing admin/device grants; do not rotate it accidentally. No server key is added to client code.
- Apply `Web/supabase-auth-security.sql` **after** baseline settings, parent-access, device and metrics migrations. It is transactional/idempotent and was applied to the configured project. Do not subsequently overwrite guarded RPCs with an older baseline migration without reapplying this security migration.
- Real PostgreSQL rollback-only assertions: `Web/qa/auth-security-transaction.sql`. Confirms shared limits, private RPC permissions, ordinary settings compatibility, AAL1 denial after enrollment, and AAL2 access. No real users or enrollments are changed; fixtures roll back.
- `node --test Web/tests/*.test.js` exercises auth methods, cross-origin rejection, encrypted-cookie binding/tampering/rotation, legacy exchange, non-secret storage, refresh races/logout, password policy/breach service failure, distributed limits, MFA enrollment/challenge/removal gates, CSP hashes, and existing app behavior.
- `node Web/qa/auth-security.cjs` uses real auth handlers and actual browser cookies against an isolated upstream fixture. Desktop/mobile checks cover cold reopen, migration, token-free storage, cookie expiry/HttpOnly, CSP injection denial, two-tab logout, and TOTP setup/login. Other settings, Undo, age-rating, navigation and browsing QA remain applicable.
- Fixture browser tests never sign in to a real user's account, enroll a real user or change a real password. Native iOS/Android/desktop hardware testing remains a manual follow-up; their existing first-party persistent browser stores are retained.
- `node Web/qa/auth-live-check.cjs` verifies the deployed CSP/build, protected admin/account/MFA APIs, foreign-origin rejection, secure cookie clearing, generic failed login, weak-password rejection and the real range-service rejection of a known breached test password. Probes use only reserved fake addresses and never authenticate or change a real account. The native 12-character minimum and current-password update requirement were independently verified after a full Supabase dashboard reload; Confirm email remained off.
